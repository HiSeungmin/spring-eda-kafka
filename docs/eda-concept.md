# 1. EDA(Event-Driven Architecture) 이란?

> ‘상태 변화’ 즉, 이벤트가 발생한 시점에 비동기적으로 상호작용하는 소프트웨어 설계 패턴

> “주문이 완료되었다”라는 사실(이벤트)을 한 번 알리면, 관심 있는 서비스들이 각자 독립적으로 자신의 일을 처리한다. 결제 시스템에 문제가 생겨도 배송 준비나 알림 발송은 영향을 받지 않는다.

## EDA 구성

- 이벤트 기반 시스템에서는 **이벤트 생성자**가 이벤트를 생성하고 **이벤트 라우터**에서 이벤트를 필터링한 다음 적절한 **이벤트 소비자**로 팬아웃한다.
    - 팬아웃(Fan-out) : 한 이벤트를 여러 수신자에게 전달하는 것을 의미한다.
    - 이벤트 라우터가 여러 소비자에게 동시에 전송하므로 각 소비자는 동일한 이벤트를 독립적으로 처리할 수 있다.

---

# 2. 핵심 용어 정리

> 이벤트, 라우터, 생성자, 소비자, 토픽 용어를 정리해보자.

| 용어 | 설명 |
| --- | --- |
| **이벤트(Event)** | • 이벤트는 **"시스템 내에서 발생한 의미 있는 상태 변화 또는 사실"** <br><br> • 특징 <br> ◦ **과거형으로 표현** : 이벤트는 이미 발생한 사실이다. <br> ‣ “주문을 생성해주세요.” (X) → “주문이 생성되었습니다.” (O) <br> ‣ `OrderCreated`, `PaymentCompleted` 등 과거형으로 작성 <br><br> ◦ **변경 불가능(Immutable)** : 한 번 발생한 이벤트는 수정하거나 취소할 수 없음 <br> ‣ 주문을 취소하고 싶다면 “주문이 취소되었습니다.”라는 새로운 이벤트 발행 <br><br> ◦ **자기 설명적(Self-describing)** : 이벤트는 무엇이 언제, 어디서 일어났는지에 대한 정보를 포함 <br> ‣ 예시 : 주문 생성 이벤트는 주문 번호, 고객 정보, 주문 시각 등을 포함 |
| **라우터(Router)** | • 라우터 또는 오케스트레이터는 이벤트 생산자를 이벤트 소비자로부터 분리하는 브로커 역할을 수행 <br> • 이벤트가 전달되는 통로 역할을 하므로 개체 간 직접 연결 없이 이벤트 전달 가능 |
| **생성자(Producer)** | • 이벤트를 생성(데이터 포함)하여 브로커에게 전달 <br><br> ⚠️ 주의 <br> • 발행자가 “누가 이 이벤트를 소비하는지”를 알고 있다면 느슨한 결합이 깨진 상태 <br> • 발행자는 이벤트를 브로커에 전달하는 것까지만 책임지고 소비자의 존재 여부나 처리 결과와 무관하게 동작해야 한다. |
| **소비자(Consumer)** | • 자신이 구독한 이벤트가 도착하면 이를 받아 처리 <br> • 이벤트 채널을 듣고 있다가 관심 있는 이벤트가 게시되면 반응 <br><br> ⚠️ 주의 <br> • 네트워크 문제나 브로커의 재전송으로 인해 같은 이벤트가 두 번 이상 도착할 수 있다. <br> • 따라서 이벤트를 여러 번 받아도 결과가 달라지지 않도록 설계해야 한다. (멱등성, Idempotency) |
| **브로커(Broker)** | • 생성자와 소비자 사이에서 이벤트를 중개하는 역할 <br><br> • 핵심 역할 <br> ◦ 이벤트 수신과 저장 : 생성자로부터 이벤트를 받아 안전하게 보관 <br> ◦ 라우팅과 전달 : 토픽이나 큐 설정에 따라 전달 경로 결정 <br> ◦ 버퍼링 : 소비자가 일시적으로 처리 불가능한 상태일 때 이벤트를 보관했다가 나중에 전달 <br> ◦ 순서 보장과 재전송 : 설정에 따라 이벤트 순서를 보장하거나 처리 실패 시 재전송 수행 <br><br> • 대표적인 이벤트 브로커 <br> ◦ Apache Kafka, RabbitMQ, AWS SQS 등 |
| **토픽(Topic)** | • 이벤트를 분류하는 논리적 채널 <br><br> • 예시 <br> ◦ 주문 관련 이벤트 → `order-events` 토픽 <br> ◦ 결제 관련 이벤트 → `payment-events` 토픽 <br><br> • 논리적 분류 단위 : 이벤트를 카테고리별로 묶는 논리적 개념 <br> • 1:N 전달 : 하나의 토픽에 발행된 이벤트는 해당 토픽을 구독하는 모든 소비자에게 전달 |

# 3. 이벤트 핵심 메시징 패턴

> Pub/Sub, Fan-out, Competing Consumers 방식을 알아보자.

## 3-1. Pub/Sub(Publish/Subscribe)

### 동작 방식

1. 발행자가 특정 토픽에 이벤트를 발행한다.
2. 브로커가 해당 토픽을 구독하고 있는 모든 소비자를 찾는다.
3. 각 소비자에게 이벤트의 사본이 전달된다.
4. 각 소비자는 독립적으로 이벤트를 처리한다.

### 특징

- 발행자와 소비자가 서로 알 필요 없어서 느슨한 결합 유지
- 소비자 수가 많아지면 브로커의 부하 증가 가능
- 이벤트 전달 순서가 보장되지 않을 수 있음

---

## 3-2. Fan-out(팬아웃)

- 팬아웃은 하나의 이벤트가 여러 소비자에게 동시에 전달되는 패턴이다.
- 예시 : 교장 선생님이 마이크에 대고 한 번 말하면, 그 음성이 모든 교실의 스피커로 동시에 전달되는 구조

### Fan-out이 유용한 시나리오

#### 1. 동일 이벤트에 대해 서로 다른 비즈니스 로직을 실행해야 할 때

- 주문 생성 이벤트 하나로 결제, 재고, 알림, 분석을 동시에 처리하는 경우

#### 2. 원본 데이터를 여러 저장소에 동기화해야 할 때

- 사용자 정보 변경 이벤트를 검색 엔진, 캐시, 분석 데이터베이스에 동시에 반영하는 경우

#### 3. 실시간 모니터링과 비즈니스 처리를 병행해야 할 때

- 트랜잭션 이벤트를 실제 처리 서비스와 모니터링 대시보드 서비스에 동시에 전달하는 경우

---

## 3-3. Competing Consumers(경쟁 소비자)

- 동일한 큐에 연결된 여러 소비자가 메시지를 나눠서 처리하는 패턴
- Pub/Sub이 “모두에게 알리기”라면 경쟁 소비자는 “일감을 나눠 처리하기”에 가까움

### 특징

- 처리할 메시지가 급증하면 워커를 더 추가하여 수평 확장 가능
- 메시지 처리 순서가 보장되지 않을 수 있음
- 같은 메시지가 두 소비자에게 중복 전달되지 않도록 브로커의 관리 필요

---

## 3-4. 세 가지 패턴 비교

| 비교 항목 | Pub/Sub | Fan-out | Competing Consumers |
| --- | --- | --- | --- |
| 메시지 전달 방식 | 구독자 전원에게 사본 전달 | 하나의 이벤트가 여러 대상으로 동시 전파 | 큐의 메시지를 소비자들이 나눠 처리 |
| 소비자 수 | 1명 ~ 여러 명 | 여러 명 | 여러 명 |
| 하나의 메시지 처리 주체 | 모든 구독자가 처리 | 모든 대상이 처리 | 하나의 소비자만 처리 |
| 주요 목적 | 관심사 분리, 느슨한 결합 | 동일 이벤트의 다중 활용 | 부하 분산, 수평 확장 |
| 적합한 상황 | 서로 다른 서비스가 같은 이벤트에 반응 | 하나의 원본 데이터를 여러 곳에 전파 | 대량 메시지를 빠르게 처리 |
| 실생활 비유 | 라디오 방송 | 학교 방송 시스템 | 패스트푸드점 주문 처리 |

> 💡 실제 시스템에서는 이 세 가지 패턴을 조합하여 사용하는 경우가 많다.
>
> `order-events` 토픽에 Pub/Sub으로 이벤트를 발행하면 Fan-out으로 결제 큐, 재고 큐, 알림 큐에 동시에 전달되고, 각 큐에서는 Competing Consumers 패턴으로 여러 워커가 메시지를 나눠 처리하는 구조가 흔하다.
>
> 이러한 조합은 느슨한 결합과 높은 처리 성능을 동시에 달성하게 해준다.

# 4. 중앙 지휘자 여부에 따른 동작

> 여러 서비스가 이벤트를 주고받으며 하나의 비즈니스 프로세스를 완성하는 방식을 살펴보자.

## 4-1. 이벤트 협업(Event Collaboration)

- 중앙에서 전체 흐름을 통제하는 지휘자(오케스트레이터)가 없음
- 각 서비스는 자신에게 관련된 이벤트를 수신하고 자신의 업무를 처리한 뒤 결과를 새로운 이벤트로 발행

### 특징

- 어떤 서비스도 다른 서비스를 직접 호출하지 않는다.
- 주문 서비스는 결제 서비스의 존재를 모른다.
- 각 서비스는 오직 이벤트에만 반응하며 자신의 처리 결과를 다시 이벤트로 발행한다.

---

## 4-2. 중앙 제어 방식(오케스트레이션)

- 주문 서비스(또는 별도의 오케스트레이터)가 전체 흐름을 직접 관리
- 중앙에서 순서와 분기를 모두 결정

### 예시

1. 결제 서비스에 결제 요청
2. 결제 성공 시 재고 서비스에 재고 차감 요청
3. 배송 서비스에 배송 준비 요청

---

# 5. 아키텍처 동작 방식 비교

> 요청/응답 아키텍처와 이벤트 기반 아키텍처의 차이를 알아보자.

## 5-1. 요청/응답 방식(Request/Response)

- 서비스 A가 서비스 B에게 직접 요청을 보내고 응답을 받은 뒤 다음 단계로 진행

### 특징

- 각 단계에서 다음 서비스의 응답을 기다린 후에야 다음 서비스 호출 가능
- 하나의 서비스 장애가 전체 호출 체인에 영향을 줄 수 있음
- 배송 서비스 장애 시 이미 성공한 결제와 재고 차감까지 롤백해야 하는 상황 발생 가능

---

## 5-2. 이벤트 기반 방식(Event-Driven)

- 주문 서비스는 “주문이 생성되었습니다.”라는 이벤트를 브로커에 발행하고 즉시 사용자에게 응답
- 이후 결제, 재고 차감, 알림 발송은 각각 독립적으로 이벤트를 받아 처리

### 특징

- 병렬 처리 가능
- 서비스 간 직접 의존성 감소
- 장애 격리 가능

---

## 5-3. 두 방식 비교

| 비교 항목 | 요청/응답 방식 | 이벤트 기반 방식 |
| --- | --- | --- |
| 통신 방향 | 서비스 간 직접 호출(1:1) | 이벤트 브로커를 통한 간접 전달(1:N) |
| 처리 순서 | 순차 처리(A → B → C) | 병렬 처리 가능 |
| 응답 대기 | 응답 받을 때까지 대기 | 이벤트 발행 후 즉시 다음 작업 진행 |
| 결합도 | 높음 | 낮음 |
| 장애 전파 | 호출 체인 전체에 영향 | 개별 장애 격리 가능 |
| 확장성 | 가장 느린 서비스에 영향 받음 | 각 서비스 독립 확장 가능 |
| 새 서비스 추가 | 호출자 코드 수정 필요 | 소비자만 추가하면 됨 |
| 전체 처리 시간 | 각 서비스 처리 시간의 합 | 병렬 처리 중 가장 긴 시간 |
| 디버깅 난이도 | 비교적 쉬움 | 비교적 어려움 |
| 데이터 일관성 | 즉각적 일관성 | 최종적 일관성(Eventual Consistency) |

> 적합한 상황에 맞게 방식을 선택해서 적용하는 것이 중요하다.

# 6. EDA의 장단점

## 장점

### 1. 느슨한 결합(Loose Coupling)

- 이벤트 생성자와 소비자가 논리적으로 분리된다.
- 서비스는 독립적으로 확장, 업데이트, 배포 가능하다.
- 다양한 언어와 프레임워크로 구현 가능하다.
- 기존 서비스 수정 없이 새로운 소비자를 추가할 수 있다.

### 2. 높은 확장성

- 기존 마이크로서비스에 영향을 주지 않고 기능 확장 가능
- 새로운 이벤트 소비자를 쉽게 추가 가능
- 시스템 간 통합이 쉬움

### 3. 비용 절감

- EDA는 푸시 기반(Push-based) 방식
- 이벤트 발생 시에만 처리하므로 지속적인 폴링 불필요
- 네트워크 대역폭, CPU 사용량 감소 가능

### 4. 장애 격리 및 빠른 복구

- 특정 서비스 장애가 전체 시스템으로 전파되지 않음

예시:
- 광고 서비스 장애 발생 시에도 주문 서비스는 정상 동작 가능

- 시스템 전체 가용성 유지 가능

---

## 단점

### 1. 복잡성 증가

- 비동기 및 분산 환경으로 인해 구조적 복잡성이 증가
- 디버깅, 모니터링 난이도가 높아짐
- 설계 및 운영 비용 증가

### 2. 데이터 일관성 문제

- 여러 서비스 간 데이터 일관성 보장이 어려움
- 전통적인 ACID 트랜잭션 보장이 어려움
- 최종적 일관성(Eventual Consistency) 기반 설계 필요

### 3. 처리 순서 문제

- 이벤트가 순서대로 처리되지 않을 수 있음

### 4. 디버깅과 테스트의 어려움

- 비동기 흐름 추적이 어려움
- 다양한 이벤트 조합 테스트가 복잡함
